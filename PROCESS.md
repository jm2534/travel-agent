# Process

## Annotated prompts

### 1. First prompt: ideas, scoping, skill introduction
- **Trying to:** fix the shape before any grilling. Before any chats, I prescribed a CLI, `pydantic-ai`, rules enforced in tools and by exceptions (per idomatic Python), and simplifications: all inventory in context, `ModelRetry` exceptions for hard rules, and constraints asserted by code. I also wanted realistic tool APIs (flights keyed by route and date, hotels by city and date) and a skeleton in about 20 minutes.
- **Got back:** a draft `REQUIREMENTS.md` on disk, and 8 questions with recommendations. These were:
  - two agents separated by a deterministic ruleset in code (extract → rules, stopping if impossible → plan)
  - clarify only when both the "what" and the "when" of the request are missing ("Cheap.")
  - the planner returns IDs (for hotels, flights, etc.), but code still prices them; no model math
  - `Infeasible` type when retries run out
  - a budget with a scope and a hard/soft flag
  - deterministic evals

  It agreed with the tool split, but pushed back on storing fixtures per date, suggesting static JSON plus a seasonal multiplier.
- **Kept / changed:** I accepted most of it, but suggested a few important quality-of-life changes (e.g., for a future developer wanting to explore the app):
  - separate models per stage (`TRAVEL_AGENT_EXTRACTION_MODEL` for Haiku, `…_PLANNING_MODEL` for Sonnet)
  - a `--from` device-location fallback for when no origin is extracted, emulating a browser's location functionality
  - fixtures generated by Haiku in a one-off script, run outside this session so it didn't fill this session's context

  The two-agent split was central to the design, and I emphasized its importance to the coding agent accordingly. It allowed us to decouple evaluation of extraction and planning phases, providing an important path in the architecture for characterizing and ultimately optimizing these agents independently.

### 2. Grilling round 2: cutting scope
- **Trying to:** settle the eval split, where rules live in the prompt context, and the output shape.
- **Got back:** a proposal to run the planner eval on *gold* constraints, three layers of prompt context (field descriptions, tool docstrings, short system prompts), clarification questions from code templates, and 1–3 ranked options.
- **Kept / changed:** I kept the gold-constraint planner eval and the templates. I cut it to **one option**, because ranking plans was overbuilding at this stage. That proved to be correct call, as we would have had to have cut ranked options anyways given that time constraints faced towards the end of the two hours. I also added `__main__.py` at this stage in anticipation of running this via a CLI.

### 3. Skeleton review: typing and style
- **Trying to:** sign off the skeleton as the design.
- **Got back:** about 550 lines of stubs with contract docstrings, a smoke test that failed against the stubs (as it should), and five design calls flagged for review. These were: tools binding the brief's fixed fields, the planner not choosing nights, the closed tag vocabulary, the room and fare rules, and 17 destinations instead of 15.
- **Changed:**
  - `str` aliases for every kind of ID (`DestinationId`, `FlightId`, `HotelId`, `AirportCode`)
  - removed the section-divider comments
  - added ruff
  - introduced `CLAUDE.md`
  - had the limitations, especially the vocabulary, written into `DECISIONS.md`

  The agent then caught its own violation of the new `CLAUDE.md`: the red smoke test broke "never leave tests failing". It marked the test as a strict xfail until the gate landed.

  The dedicated key types, even as aliases for a string and though apparently minor, are important in my experience for keeping code readable. I've personally been in LLM-heavy codebases where string keys are allowed to proliferate, and it becomes impossible in the long run to tell data, e.g. prompts and queries, from domain entites like keys. It also allows us to add constraints, validators, etc. to the type without worrying about type references needing to change (from `str` to some new type). 

### 4. Pushing back on silently ignoring an end date that conflicts with stated nights
- **Trying to:** approve the slice 1 plan for the gate
- **Got back:** a proposed rule that when an explicit end date and the stated nights disagree, "nights wins and end is ignored"
- **Changed:** "that needs to be flagged as a caveat; 'end is ignored' can't be done silently." The result is the `END_DATE_IGNORED` caveat, with the spec updated first, then the test, then the code. It's the same principle as the budget handling: degrade if you have to, but never silently

This was one of a few instances in which I emphasized the importance of providing caveats to the user instead of failing to handle constraints, even contradictory ones, silently. This is I think an important design principle for this sort of app if made into a product: have the model find as reasonable a travel plan as it can, flagging deviations to the user and escalating only when unable to continue productively (the missing "where" and "when" mentioned above). For other use-cases this may not be the best heuristic, for instance if there were any write paths involved, e.g. booking the trip itself.

### 5. Both test reviews found tests that were too easy to pass
- **Trying to:** check that each slice's tests would actually catch a broken requirement, using a fresh-context reviewer before implementation.
- **Got back:**
  - *Slice 1:* the end-date conflict test used a degenerate range (Oct 13 to 13). The "Cheap." test passed with *all* fields empty, so it couldn't tell "nothing about what or when" from "nothing at all". Three rules existed only in docstrings, not in the spec
  - *Slice 2:* the fixtures were already in price order, so a tool that never sorted passed "cheapest first". There were no passing cases for the hotel requirements or exclusions. The 1500 km `near` boundary was never tested. And the spec promised "`[]` plus a reason", which no tool returned
- **Kept / changed:** I fixed every finding, spec first. The fixture order was reversed, and Lyon (inside 1500 km) and Rome (outside) were added to pin the boundary. The lesson: the agent wrote tests that matched its own fixtures. A reviewer with a fresh context found that in about a minute, every time

### 6. Keeping the code navigable: top-level functions and factories
- **Trying to:** keep files readable as they grew. `plan.py`, `gate.py`, `pricing.py` and `tools.py` each had 11 to 13 top-level definitions
- **Asked for:** factory methods (e.g. `Catalog.load`) and fewer top-level functions.
- **Got back:**
  - a refactor with no behaviour change: records price themselves (`Flight.price_for`, `Hotel.nightly_rate` and `Hotel.rooms_for`)
  - the date helpers moved onto `ResolvedDates`, which took `gate.py` from 11 top-level definitions to 4;
  - `DestinationMatch.of`
  - one `spend_against` that both hard caps and soft-budget caveats use

  Method vs. class ownership has always been a challenge in program design, and I sometimes find coding agents land on one extreme by preferring simple, top-level methods to such an extent that the program flow is hard to follow. Classes, especially when taken to be namespaces holding business logic, can help with that. For modules (here, Python files) with clear existing responsibilities, a simple prompt with example (as I provided, see transcript) is often enough to get the design on track: note the model's correct interpretation of this preference in leaving [pricing.py](src/travel_agent/pricing.py) at 8 definitions on purpose, because the rule-checks read as a list. A class `Rules` or similar holding all of these would have been counterproductive and was avoided.

### 7. The first real run returned an honest `Infeasible` rather than a plan that silently broke the budget
- **Trying to:** run example 1 end to end with real models: "beach week in February under $2000 for two from JFK, nice hotel"
- **Got back:** `infeasible`. The planner searched 6 beach destinations and checked them with `quote_trip`. Code priced its closest option at $3,267, an `OVER_BUDGET` violation. The reason told the user what *would* work: 3-star hotels, or about $3.1k
- **Kept:** "nice hotel" maps to a hard 4-star minimum, documented as a known gap rather than tuned away. The agent pointed out that the dollar figures in the model's free-text `reason` aren't validated; only `cost` is authoritative. That's in the known gaps too

  This was great signal within the dev loop, helping to confirm some edge-case definitions while also testing end-to-end functionality.

### 8. Final reviews: quick wins now, the rest handed off
- **Trying to:** run final review-against-spec while the eval ran
- **Got back:** 10 requirements findings and 14 standards findings. Real bugs among them
  - `--from jfk` caused a traceback
  - the model could declare a feasible request infeasible with nothing checking it
  - "Dec 1–1" became a 365-night trip
- **Kept / changed:** the must-fixes, the cheap cleanups and the spec drift were done, each with a test. Everything else went into a written handoff prompt for the next session rather than squeezed in.

  Context discipline (after seeing more than >25% usage) remained a priority even during the busy end of the development time.

## Evaluation
**Design:** 9 cases (`evals/cases.yaml`): the 7 assignment prompts, a contradictory one (a 5-star Barcelona week for $800), and one with no data (Reykjavik). Each case is scored **twice, independently**:

| Stage | Input | Dimensions |
|---|---|---|
| Extraction | raw request | `fields`: a partial match of expected fields (lists as subsets); `routing`: the real gate, run on the extracted constraints, agrees on ask vs. plan |
| Planner | **gold** constraints | `outcome` type; `adherence` to case-level hard checks (caps, amenities, style, allowed or forbidden destinations, region); expected `caveats` present |

The planner runs on gold input, so an extraction error can't hide a planner failure or fake a pass. All scoring is deterministic. Expected outcomes were checked against the data. Model-free tests keep the cases consistent: gold must satisfy its own extraction expectations, and the expected gate caveats must match the gate exactly.

**Results:** 
- Run 1 (`cadb077`): extraction fields 8/9, planner caveats 8/9 
- Run 2 (`d8b4225`): 9/9 on every dimension
- Run 3 (final, `d581d8e`): 9/9 as before

**What it doesn't measure:**
- the quality of the reasoning text (no LLM-as-judge)
- variance across runs (each case runs once)
- inputs outside the closed tag vocabulary

## Reflection

### Overall approach
I first set up the repo with a handful of custom skills that I've built over the past few months, shared here for review. They're standard spec-driven development tooling with an emphasis on delivering incremental functionality in "slices" with subagent-based review. This workflow takes heavy inspiration from conventional programming wisdow; see "tracer bullets" and similar ideas in standard reading like [The Pragmaitic Programmer](https://en.wikipedia.org/wiki/The_Pragmatic_Programmer). 

I use Claude Codex in tmux to jump between sessions and terminals, and review diffs in Zed (though have been making more use of `/diff` as its improved). I encrypt secrets via [age](https://github.com/filosottile/age) and keep the cyphertext in `.env.age`, which can be decrypted and loaded via [direnv](https://direnv.net/) automatically into any shell that navigates to the repo. I `.gitignore` these for simplicity in onboarding to the repo (since only I would be able to use them), but they could be freely committed.

The skills, in the order they ran:

- **`grill-to-requirements`** (wraps `grilling`): drafts `REQUIREMENTS.md` straight away, then asks numbered questions, each with a recommended answer. It stops after about three rounds; anything still open becomes a recorded assumption.
- **`build-in-slices`**: first a runnable skeleton of stubs. Then one requirement at a time, in order: stubs, tests, a test review, red against the stubs, the implementation, then my read of the diff.
- **`review-against-spec`**: a fresh-context subagent in `tests` mode checks that the tests would fail if a requirement broke. In `final` mode, two subagents check requirements coverage and code standards.
- **`CLAUDE.md`**, added after the skeleton: workflow and style rules. These include business rules in code rather than prompts, typed boundaries, a test and commit for every behaviour, and decisions logged as "X over Y because Z" in `DECISIONS.md`.

Two rounds of planning in about 20 minutes, followed by a skeleton, then for most of the time iterating on the slices. I reviewed the skeleton and `REQUIREMENTS.md` spec carefully, especially against what `ASSINGMENT.md` specifies, and then moved more quickly through the slices. The skills were important in maintaining quality by bubbling up the important design-oriented or otherwise blocking decisions to me directly while handling subagent code review and test results automatically.  

From slice 1 onwards, every slice was built in its own git worktree. That let me read and merge one slice while the agent built the next, without changes appearing under me. Reviewer subagents were also brought in for repeated adversarial reading of tests, per the skills.

**Time spent:** 4:05pm - 6:05pm development time on 11/12/2026, about the same amount of time to finalize the reflection (no code modifications

### Review
With the slice-based approach, the agent typically provides narrow diffs rather than huge commits. That said, I focused my review as usual on specification, data models, and interfaces, especially early on, since they're the basis for everything else.

I manually review data models (here, Pydantic `BaseModels` that get type and structural validation for free) for soundness - whether their fields have correct constraints and types, whether they have sensible operations defined, and whether those operations correctly capture the business rules defined in the requirements. I also review system prompts and docstrings line-by-line, since they're central to the context sent to the model. Unit tests I typically review, though I was pressed for time towards the end of the build and didn't get to fully check slice 3's tests.

After methods are written, I typically scan the implementation for any obvious issues, but don't necessarily go line-by-line, preferring especially for some of the denser blocks, e.g. `_id_violations` in [pricing.py](src/travel_agent/pricing.py) to keep interfaces narrow and unit test the method's contract.

### What I'd do differently
- Get signal sooner into the dev loop from the eval harness - `age` wasn't decrypting the secrets I had in the repo into the Claude session, but beyond that the eval harness wasn't codified as part of this repo's dev loop (though the models did reach for it on their own)
- LLM-as-judge, albeit uncalibrated, would be nice here: a bigger model able to sanity check how aligned the reasoning is with the product vision is a useful output, especially in early stages when iterating rapidly
- Introduce CLAUDE.md before the skeleton, not after; the skeleton needed a style pass because of it. It was an oversight on my part, but I caught it early enough after realizing my style guide wasn't being followed
- Consider detecting and raising elements missing from the travel vocabulary (`Tag`, `Region`, `Amenity`, `HotelStyle`) to the user, since missing entities are currently silently ignored
- Test reviewer for mutation-style checks from the start (e.g. "would this pass if the sort were removed?"). Early reviews found exactly that class of weakness multiple times

### If this had to run at 10k requests an hour
- **Models:** keep the agent split, with a smaller model still for extraction. Planning probably doesn't need a full tool loop for most requests: retrieve candidates in code (filter, rank, price), then have one model call choose between already-priced options. That cuts latency and cost, and removes most of the retries.
- **Prompting:** cache the static prefix (instructions plus tool and output schemas) with prompt caching
- **Schema:** the closed vocabulary becomes a real limitation. Map unknown preferences to an "unmatched" list with a caveat instead of dropping them, and version the schema so evals pin to a version.
- **Validation:** keep code as the contract. Add a hard limit on tool calls per request, and record which violation kinds trigger retries, as a quality signal.
- **Evals:** grow the cases from sampled production traffic, running each case N times though the deterministic checks in addition to an LLM-as-judge for end-to-end reasoning, calibrated against a small hand-labelled set.
- **Ops:** move the eval set to an async batch and cap concurrency per provider. For the app itself, fall back to a second provider on `ModelAPIError`, e.g. due to rate limits, if one is available. Logging/instrumentation/LLM observability more generally to trace failures that occur at this scale
